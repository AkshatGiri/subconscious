Brain-Inspired Memory Engine — Complete Design Brief
                                                                                                                                                            
  Vision                                                          

  A standalone, harness-agnostic memory engine that mirrors human memory architecture. It ingests raw conversations and information in real-time, manages a
  graph-structured memory store with consolidation and decay dynamics, and uses a background LLM ("subconscious") for autonomous memory management. Thin
  adapters wire it into any AI harness (OpenClaw, Claude Code, OpenCode, Codex, etc.).

  ---
  Core Data Model — Four Layers

  Layer 0: Sensory / Conversation Log
  - Raw conversation transcripts logged in real-time as they happen
  - Append-only, immutable source of truth
  - This is the sensory/short-term input — the firehose of everything that comes in
  - Indexed and searchable (full-text + embeddings)
  - Retention policy: configurable age-out or compression for old transcripts
  - Every higher-level memory traces back here via sourced_from edges

  Layer 1: Short-Term Memory
  - Rolling summary of the current/recent conversation
  - Last N messages in working buffer
  - Ephemeral — scoped to the active session
  - Automatically maintained as conversation progresses (the subconscious keeps the summary current)
  - This is the "what just happened" and "what we're talking about right now"

  Layer 2: Long-Term Memory (Graph)

  Persistent graph store. Nodes are memories, edges are relationships.

  Node types:
  - Semantic — facts, preferences, knowledge ("user prefers Bun", "project uses PostgreSQL")
  - Episodic — events with temporal anchoring ("Feb 20: debugged auth bug, root cause was stale token")
  - Procedural — workflows, patterns, how-to knowledge ("deploy process: test → build → push → verify")

  Edge types:
  - related_to — topical association
  - caused_by / led_to — causal chain
  - supersedes — updated information replacing old
  - reinforces — corroborating evidence
  - contradicts — conflicting information
  - sourced_from — provenance link back to conversation log
  - part_of — hierarchical grouping

  Tagging dimensions on each node:
  - Topical — domain/subject (auth, deployment, preferences, project-X)
  - Categorical — memory type (fact, decision, preference, event, workflow, person, entity)
  - Contextual — origin metadata (channel, session, agent, timestamp, who said it)

  Memory dynamics on each node:
  - Strength — increases on recall/reference, decays over time without use
  - Recall count — how often this memory has been accessed
  - Last accessed — timestamp of most recent retrieval
  - Created from — link to source conversation/summary
  - Confidence — how certain the extraction was

  Layer 3: Working Memory
  - Not stored — computed at recall time
  - The ~7 most relevant memories assembled for the current context
  - Selected by the recall engine from the graph using: relevance + recency + strength + associative proximity

  ---
  The "Subconscious" Background LLM Agent

  An autonomous background process that manages the memory system. Mirrors the brain's unconscious memory management (hippocampal replay, sleep
  consolidation).

  Responsibilities:

  1. Extraction — After ingestion, analyze conversations and pull out structured memories (semantic facts, episodic events, procedural patterns). Determine
  type, tags, importance.
  2. Association — Discover relationships between new and existing memories. Create edges. "This new preference about Bun relates to the Node migration
  decision from last week."
  3. Consolidation — Periodically review short-term buffer. Promote worthy memories to long-term. Merge duplicates. Resolve contradictions (mark old as
  superseded).
  4. Summarization — Generate and maintain conversation summaries. Update rolling short-term summary as conversation progresses.
  5. Decay & Strengthening — Memories that get recalled often have their strength increased (hardening). Memories that go unreferenced decay over time.
  Eventually forgotten (soft-deleted or archived, not hard-deleted — the brain doesn't truly delete either).
  6. Surfacing — During recall, help select the optimal working memory set. Not just vector similarity — consider the graph neighborhood, temporal
  relevance, and conversation trajectory.
  7. Contradiction Resolution — When new information conflicts with existing memories, decide: supersede, flag for user confirmation, or store both with a
  contradicts edge.

  ---
  Core Engine API

  // Ingestion
  ingest(conversation)     — log raw conversation, trigger extraction
  ingest(document)         — index a document, extract memories
  ingest(fact)             — directly store a structured memory

  // Retrieval
  recall(query, context?)  — assemble working memory (~7 items) from graph
  search(query, opts?)     — traditional search across all layers
  get(memoryId)            — fetch a specific memory + its graph neighborhood
  trace(memoryId)          — follow sourced_from back to raw conversation

  // Management
  consolidate()            — trigger consolidation cycle
  forget(memoryId)         — manually mark for decay/removal
  reinforce(memoryId)      — manually strengthen a memory
  associate(a, b, edge)    — manually create a relationship
  status()                 — health, stats, memory counts by type/strength

  ---
  Retrieval Strategy

  When recall() is called:

  1. Vector similarity — find candidate memories by embedding similarity to the query
  2. Graph traversal — expand candidates by following edges (associated memories, causal chains)
  3. Recency weighting — boost recently created/accessed memories
  4. Strength weighting — boost frequently recalled (hardened) memories
  5. Salience scoring — combine all signals into a final rank
  6. Working memory selection — pick the top ~7, balancing diversity (don't return 7 variations of the same fact)
  7. Context assembly — format for injection into the agent's context, with appropriate detail level (summary vs. full)

  If the agent needs more detail on a recalled memory, it can trace() back to the source conversation.

  Platform Adapter Interface

    onSessionEnd(session)         → engine.consolidate()

    // Engine provides these to the platform:
    getTools()                    → tool definitions for the agent
    getWorkingMemory(query)       → formatted context string for injection
  }

It’s the engine’s “forgetting curve.”

- `nextStrength = clamp(currentStrength * factor, minStrength, 1.5)`
